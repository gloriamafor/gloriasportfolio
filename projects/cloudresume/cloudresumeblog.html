Cloud Project Case Study

How I Built the Cloud Resume Challenge

A step by step walk through of how I deployed my portfolio on AWS as a fully serverless site, built a visitor counter with Lambda and DynamoDB, hosted my personal projects on it, and later rebuilt the backend in Terraform to deepen my infrastructure-as-code skills.

Why I did it

Proving cloud skills by building, not just studying

I wanted a way to show that I could work with real AWS services end to end, not just pass a quiz about them. The Cloud Resume Challenge is perfect for that: you host your resume as a live website and, by the time you are done, you have touched storage, a content delivery network, DNS, HTTPS certificates, serverless compute, a database, infrastructure as code, and automated deployments. Every major piece of cloud engineering in one project.

So I turned my portfolio at gloriamafor.com into that project, and then used it as a home for my personal applications too.

The big picture

How the whole thing fits together

There are two halves: a static frontend that serves my site, and a small serverless backend that powers a visitor counter.

Frontend

Visitor→ Route 53 (DNS)→ CloudFront (CDN + HTTPS)→ S3 (site files)

Backend (visitor counter)

Browser→ API Gateway→ Lambda (Python)→ DynamoDB
Part 1

Hosting the portfolio from start to finish

Register the domain

I registered gloriamafor.com through GoDaddy. The registrar owns the domain name, but it does not have to be the thing that answers DNS questions or hosts the site. I kept those jobs on AWS.

Store the site in S3

I created an Amazon S3 bucket and uploaded my static files: the HTML, CSS, JavaScript, images, and project pages. S3 is object storage, so there is no server to manage. It simply holds the files and hands them out.

Put CloudFront in front of it

I created a CloudFront distribution with the S3 bucket as its origin. CloudFront is a content delivery network, so it caches my site at edge locations around the world, which makes it load faster, and it is also where HTTPS is handled.

Point the domain at AWS with Route 53

I created a hosted zone in Route 53, then went back to GoDaddy and replaced its nameservers with the Route 53 ones. That is called delegation: GoDaddy still owns the registration, but Route 53 now answers for the domain. Then I added records that point the domain at my CloudFront distribution.

Turn on HTTPS with ACM

I requested a TLS certificate from AWS Certificate Manager and validated it through DNS. One detail that trips people up: for CloudFront, the certificate has to live in the us-east-1 region, no matter where the rest of your resources are. Once it was attached, the site served securely over HTTPS.

At this point I had a live, secure, globally distributed portfolio, with no server to patch anywhere.
Part 2

The serverless visitor counter

A static site cannot count its own visitors, so I built a tiny backend that does. Nothing runs until someone loads the page.

DynamoDB for the count

I created a DynamoDB table called portfolio-visitor-count with on-demand billing, so I only pay per request. It holds a single item with the running total. The important trick is how I update it:

table.update_item(
    Key={"id": "visitorCount"},
    UpdateExpression="ADD #views :increment",
    ExpressionAttributeNames={"#views": "views"},
    ExpressionAttributeValues={":increment": 1},
    ReturnValues="UPDATED_NEW"
)

Using ADD increments the number inside DynamoDB in one atomic operation. If I had read the value, added one in my code, and written it back, two visitors arriving at the same time could overwrite each other and the count would drift. The atomic add avoids that completely.

Lambda for the logic

The code above lives in an AWS Lambda function written in Python. Lambda only runs when it is called, scales on its own, and I never manage a server. It reads the table name from an environment variable and has permission to touch only that one table, which is the least-privilege approach.

API Gateway for the endpoint

To let my website call the function, I put an API Gateway HTTP API in front of it with a single route, GET /count. The function also returns CORS headers so the browser is allowed to call it from my domain. My site's JavaScript calls that endpoint on load and displays the number it gets back.

Part 3

Infrastructure as code and automated deploys

Clicking around the AWS console is fine for learning, but it is not repeatable. So I defined the backend as code.

AWS SAM

I used AWS SAM, which is a shorthand layer on top of CloudFormation built for serverless apps. One template file describes the DynamoDB table, the Lambda, its permissions, and the API, and sam deploy builds it all. That means I can tear the whole backend down and stand it back up from one file.

CI/CD with GitHub Actions

I set up a GitHub Actions workflow so that every time I push to my main branch, it runs my tests first, and only if they pass does it build and deploy the backend. A failed test cancels the deploy, so I cannot ship something broken by accident.

Part 4

Hosting my personal projects on the cloud

Once the portfolio was live, I used it as a home for the projects I had built.

Food Recommendation Generator

This one is a web app that suggests recipes. The frontend is static, so it lives in S3 and is served through CloudFront like the rest of the site. The recommendation logic is Python, and because S3 cannot run Python, I adapted that logic into a Lambda function and exposed it through API Gateway, so the browser frontend can call it for live recommendations. It is an ETL-style workflow: it pulls recipe data from an external source, transforms and filters it, and returns structured results.

Movie AI Recommendation System

My mood-based movie recommender runs as a live Streamlit app, so rather than rebuild it on AWS I showcased it on the portfolio and linked out to the running application. Sometimes the right call is to host a project where it already works well and point people to it.

Marital Satisfaction Prediction Model

This is a machine learning project, so I presented it as a showcase: the write-up, the charts, and the results, all served as part of the static site.

Part 5

Taking it further: rebuilding the backend in Terraform

I originally deployed the backend with SAM because that is what I knew at the time. As I started learning Terraform, I went back and rebuilt the same backend in it, on purpose, to practice an infrastructure-as-code tool that works across clouds, not just AWS.

In Terraform there is no serverless shorthand, so I had to write each piece out explicitly: the DynamoDB table, the Lambda's IAM role and a least-privilege policy, the function itself (packaged with an archive_file instead of sam build), and the HTTP API with its integration, route, stage, and the permission that lets API Gateway invoke the function. Writing it all out actually helped me understand what SAM had been doing for me quietly.

A real bug I hit, and how I fixed it: my first terraform apply failed with ResourceInUseException: Table already exists. My old SAM stack still owned the table name, and two tools cannot manage the same named resource. I deleted the SAM stack, re-applied, and let Terraform own the backend cleanly. Then I updated the frontend to the new API URL and invalidated the CloudFront cache, because updating a file in S3 does not change what CloudFront is already serving.

That is the kind of lesson you only get by actually deploying something and watching it break.

What broke, and what I learned

Troubleshooting and lessons

  • HTTP versus HTTPS: getting CloudFront and the ACM certificate working together so the site is secure, including the detail that the cert must be in us-east-1.
  • 403 Access Denied from S3: sorting out how CloudFront is allowed to read the bucket.
  • DNS delegation: coordinating GoDaddy's nameservers with the Route 53 hosted zone so the domain resolves to CloudFront.
  • CORS: making sure the API returns the right headers so the browser is allowed to call it.
  • Lost updates: using an atomic DynamoDB add so simultaneous visitors cannot overwrite the count.
  • CloudFront caching: remembering to invalidate the cache after a change, because the edge keeps serving the old files until you do.
  • One name, one owner: you cannot have SAM and Terraform both managing a resource with the same name. Pick one.
Where I would take it next

What I'd improve

  • Swap the long-lived AWS keys in my deploy pipeline for OIDC, so GitHub Actions assumes a short-lived role instead of storing static secrets.
  • Put the frontend in infrastructure as code too, so the S3 and CloudFront setup is codified alongside the backend.
  • Scope the API's CORS to just my domain instead of allowing any origin.
  • Move Terraform's state to a shared remote backend, so it could be managed by a team instead of from my laptop.
